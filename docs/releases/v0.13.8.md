# v0.13.8

## Settings schema installs on a Dynatrace tenant

- The Forward URL pattern added in v0.13.7 was rejected by the Dynatrace settings service at install time. Dynatrace
  requires lazy quantifiers inside any regex group, and the v0.13.7 pattern used greedy ones, so the
  `forward-api-connection` schema failed validation and the app did not install.
- The pattern is now a plain top-level alternation with no groups: an HTTPS origin, or an HTTPS origin ending in `/api`.
  Origin-form and legacy `/api` values are accepted, and credentials, query strings, fragments, HTTP URLs, and other
  paths are rejected. The schema no longer checks port or bracket syntax, so a malformed value such as `https://host:abc`
  now passes the schema and is rejected by the backend's URL parsing instead.
- The backend still parses the URL strictly (`lib/forward-connection.ts`), so the schema pattern is only the first check.

## Upgrade note

v0.13.7 was never installed successfully on a tenant. Deploy v0.13.8 as a new immutable app version. A failed install of v0.13.7 can
leave that version registered on a tenant with a different checksum, so it cannot be redeployed.

## Source verification

The new pattern was checked against 15 accepted and rejected URL forms, and v0.13.8 installed on a Dynatrace trial
tenant. The v0.13.7 miss is why the install matters: the repository CI passed and the install still failed, because
nothing in CI validated schema patterns the way the Dynatrace settings service does. v0.13.8 adds that check
(`dynatrace:regex:test` and a rule in `repo:validate`) for greedy quantifiers inside regex groups. See the
[live trace acceptance record](../acceptance/2026-10-15-v0.13.8-live-trace-plan.md).

## Secret And Identity Findings

- The Forward credential is stored in an AppEngine-scoped Dynatrace Credential Vault entry. Owner-only user access is
  enabled, ad hoc/no-app-context access is off, and external-vault synchronization is off.
- The tenant's **Dynatrace apps with access** selector did not offer either `my.forward` or `Forward`; only **All
  applications** was available. The unsaved restriction probe was discarded to preserve the working connection. This
  remains a production least-privilege blocker.
- The current Forward API token resolves to a human-backed local identity with organization-administrator privilege,
  not an integration-named least-privilege service identity. A read-only API attempt to enumerate administrator users
  was denied with HTTP 403. A Forward administrator must provision the dedicated service identity and rotate the Vault
  secret before production.

## Explicitly Not Done

- No Workflow schedule was created.
- No Network Admin connection was saved or exercised inside Dynatrace. The bounded write rehearsal used the exact
  v0.13.4 action logic and protected lab credentials outside the tenant, so an installed Vault-backed Network Admin
  Workflow remains a production-promotion gap.
- No customer or production Forward checks were changed. The isolated lab created one acceptance check, removed that
  exact check, updated five managed checks, and restored the verified baseline.
- No production customer telemetry was claimed.
- No customer-query pilot was claimed; the only ready discovery profile was the containerlab OTLP lab profile.
- No signed `com.forward.dynatrace` distribution was claimed.

The next production-readiness review must require the dedicated Forward service identity, exact-app Vault scope or an
approved tenant fix, signed distribution, customer-owned telemetry mapping, operating cadence, and write-approval and
rollback ownership.
